5. GAMEPLAY HANDLERS
MotherSearch.catchPlayer selects the appropriate confrontation before applying
the existing relationship changes. Inventory inspection requires proximity and
line of sight; genuine owner-bound evidence determines restricted-item discovery.
Confirmed evidence is recorded in the existing permanent exposed-secret set.
Secret-area classification uses generated room metadata, including nearby entrances.
One encounter latch prevents repeated penalties/dialogue while Mother remains nearby.
After sustained separation, a later encounter may trigger a fresh confrontation.

6. BLACKMAIL FLOW
Validate owner/item/interaction -> capture relationship state -> queue offer voice
-> wait for recording duration and playback acknowledgement -> roll outcome once.
Acceptance opens the existing reward picker. Only successful inventory insertion
or owner-bound overflow spawn commits consumption/consequences and queues acceptance.
A failed spawn retains the reward choice, receipt and capability for retry.
Closing the picker is recoverable: right-click Mother to reopen the same reward
selection without creating a new offer or rolling the outcome again.
Rejection consumes the capability once, applies the existing penalty once, records
source-secret exposure and queues rejection. Both outcomes expose source secrets.
Right-click spam cannot create overlapping offers. Saved transaction state survives
ordinary save/reload. A bounded missing-playback fallback prevents a missing sound
acknowledgement from permanently blocking resolution.

7. CONFRONTATION PRIORITY
Actually discovered restricted items > metadata-classified secret area > ordinary
restricted area. Exactly one confrontation is selected, not all three in sequence.
Dialogue code does not apply a second copy of the gameplay penalties.

8. RELATIONSHIP STATE / RANDOMIZATION
Uses OtherMotherLoopState.classify with the existing five states and thresholds.
The state captured at encounter/offer start is retained through that transaction's
outcome, even if relationship values subsequently change. Future encounters use
updated values. Existing last-variation tracking prevents immediate repetition.

9. DEBUG CONTROLS
Secrets Debugger -> Voice tab (operator-only).
Choose event, state, and Random/1/2, then Play voice (no penalties).
Actual event (real consequences) exercises the gameplay pathway separately.
Forced blackmail outcomes still require a genuine owned blackmail item. Actual
confrontations classify the current location/evidence rather than forging evidence.
Audio and state changes remain targeted to the storyline owner.

11. AUDIO QUALITY CHECKS
All final WAVs decode as mono 22050 Hz PCM16. Generation checks reject invalid
duration, silence and clipping; leading/trailing silence is trimmed with handles,
not by cutting spoken endings. Active loudness is normalized consistently with the
existing pipeline. No time-stretching is used. Runtime Vorbis exports preserve
duration; source/runtime differences must be under 0.05 seconds.
Every final recording underwent Whisper transcription and CAMPPlus comparison with
the unchanged reference. Nonexact transcripts received a second beam-search decode.
Checks also verify all 60 registrations, exact subtitle text, and duration metadata.
Reports: voicelines/othermother/secrets/generation_report.json,
validation_report.json and transcript_review.json.

13. LIMITATIONS
All 60 requested recordings are generated, registered and integrated; no requested
event/state pair is left as a text placeholder.
Automated transcription/speaker checks do not prove subjective acting quality or
replace a human listening review of every line. Some spoken contractions expand
naturally (for example, "here's" becomes "here is").
Owner isolation is covered by server tests; no two-human-client multiplayer session
has been performed. No destructive process-kill/power-loss fault injection has been
performed. Reward receipts guard ordinary retries/replays, but cross-file player/
world saves are not claimed to be atomic against arbitrary power loss.
